How the judge actually works

A code execution engine that runs untrusted programs inside locked-down containers, an asynchronous grading pipeline built on top of it, and a real-time layer that pushes results back to the browser. This page explains every moving part and why it is shaped that way.

01 — The shape of the system

Two things, not one

The single most important idea in this architecture is a line between two concepts that are easy to confuse:

Execution
Given a language, some source code, and standard input: run it in isolation and report what happened — stdout, stderr, exit code, CPU time, peak memory. It knows nothing about problems, test cases, or verdicts.
Grading
Given a problem and a submission: fetch that problem's test cases, call execution once per case, compare each output against what was expected, and aggregate a single verdict.

Grading is a consumer of execution, not a peer of it. Once that line exists, the engine can serve other clients too — which is exactly what the public API in section 07 does.

02 — The parts

What each component is for

Six pieces, each solving one problem. The reason there are six rather than one is that judging code is slow and dangerous, while serving a web request should be fast and safe.

API server
Express
Accepts HTTP requests and holds open WebSocket connections. Everything it does is fast: write a row, push an ID onto a queue, read a row back. It never waits for code to be judged.
PostgreSQL
The source of truth. Problems, test cases, users, submissions, results. Anything that must survive a restart lives here, and any component that needs the real state reads it from here rather than from a message.
Redis Stream
the queue
Holds submission IDs waiting to be judged. Durable: a message stays claimable until a worker explicitly acknowledges it, which is what makes a mid-judge crash survivable.
Worker pool
Separate process. Pulls IDs off the queue, loads the real submission from Postgres, drives the grading loop, writes results back. Several consumers run at once, each on its own Redis connection.
Sandbox container
One throwaway Docker container per run, with a hard memory cap, a process-count cap, no network, and a non-root user. This is where untrusted code actually executes.
Redis Pub/Sub
+ WebSocket hub
The notification path. The worker announces "submission 482 is done"; the API server, which holds a single standing subscription, forwards that to whichever browsers asked about 482.
The distinction people miss

The Stream and Pub/Sub are both Redis, but they are not the same tool. The Stream is a queue — it holds work until someone acknowledges it. Pub/Sub is a loudspeaker — it holds nothing, and a message sent while nobody is listening is simply gone. The queue carries the work; Pub/Sub only carries the announcement that the work is finished.

03 — End to end

One submission, all the way through

Nothing in this path blocks on anything slow. The browser gets an answer in milliseconds; the actual judging happens on its own schedule and reports back when it's done.

  1. The browser sends POST /submissions with the problem, language, and source code.
  2. The API server writes a row into Postgres with status Queued. That row is now the only authoritative record that this submission exists.
  3. The API server does XADD onto the Redis Stream carrying only the submission's ID — not the code.
  4. The API server immediately replies with the submission ID. The HTTP request is finished; nothing waited on judging.
  5. The browser opens a WebSocket and subscribes to that ID. The server notes which connection cares about which submission, and immediately sends back the current status read from Postgres (section 06 explains why that read matters).
  6. Independently, a worker blocked on XREADGROUP wakes up, claims the ID, and loads the real submission and its test cases from Postgres.
  7. The worker creates one sandbox container, compiles once, then runs each test case through the compiled program, stopping at the first failure.
  8. The worker updates the Postgres row with the verdict and per-test results, then XACKs the queue message to mark the work genuinely done.
  9. The worker publishes a short "submission 482 is done" message on Redis Pub/Sub.
  10. The API server's standing subscriber receives it, looks up which WebSocket connections asked about 482, and pushes the update to exactly those. The page updates without a refresh.
Why the queue carries only an ID

If the message carried the source code too, the queue would become a second place where a submission's state lives — and two sources of truth eventually disagree. Carrying only an ID makes the message a pure notification: "go look at row 482." Postgres stays the one thing that knows what row 482 actually contains.

04 — Containment

How untrusted code is contained

The code being run is written by strangers and may be hostile, broken, or accidentally catastrophic. Two different Linux mechanisms do the containing, and they are commonly confused with each other.

Namespaces control what a process can see — its own process tree, its own filesystem view, its own (absent) network. Control groups control what a process can use — how much memory, how many processes, how much CPU. Docker is a convenience wrapper that sets both up, plus image packaging.

How each verdict is actually determined

VerdictDetected by
AcceptedExit code 0 and output matches expected, for every test case.
Wrong AnswerExit code 0 but output differs from expected. Grading stops at that test.
Compile ErrorThe compile step returned a non-zero exit code; its stderr is shown to the user.
Time Limit ExceededThe wall-clock timer fired before the run finished. The container is killed in a finally block so nothing is left running.
Memory Limit Exceededdocker inspect reports State.OOMKilled = true — the kernel, not a guess. Exit code 137 (128 + SIGKILL) corroborates it.
Runtime ErrorNon-zero exit code with no OOM kill: a crash, an uncaught exception, or a deliberate non-zero return.

One design decision worth being able to defend: grading stops at the first failing test. Partly because it matches how real judges report ("Wrong Answer on test 2") and saves compute on submissions already known to be wrong — but also because OOMKilled is a property of the whole container's history. Continuing to reuse a container after one test has already been OOM-killed means reading stale kill state on the next test. Stopping avoids that class of bug entirely.

05 — The queue

Why a queue instead of just calling the function

The API server could simply call the grading function directly and wait. Three things break if it does.

It blocks. Node runs one thread; a request stuck for five seconds waiting on a container blocks every other request queued behind it.

It loses work. If the process dies mid-judge, that submission is gone with no record that it was ever in progress.

It cannot scale separately. Grading and serving HTTP have completely different resource profiles, and a direct call welds them into one process that must scale as a unit.

What a consumer group actually does

When a worker calls XREADGROUP, Redis does two things: it hands over the message, and it records in a pending entries list that this specific consumer holds that message and has not acknowledged it. XACK is what removes that record.

So if a worker dies halfway through judging, the entry is never acknowledged and never disappears — it sits in the pending list, visibly held by a consumer that no longer exists. Another worker can then claim it with XCLAIM or XAUTOCLAIM once it has been pending too long. The job isn't lost; it's parked in a recoverable state.

Why every consumer gets its own Redis connection

A blocking XREADGROUP occupies its connection while it waits, and a single connection handles one command at a time. Three consumers sharing one connection would take turns rather than working in parallel — the second consumer couldn't even issue its read until the first returned. Separate connections let three blocking reads be outstanding simultaneously, which is what makes the pool actually concurrent.

06 — Real time

Live updates, and the race hiding in them

Ordinary HTTP is a postcard: one request, one reply, connection closed. To learn when grading finishes, a browser would have to keep asking. A WebSocket is a phone call left open instead — either side can speak at any time, so the server can announce the verdict the moment it exists.

Opening the connection isn't enough on its own, though: the server may be holding hundreds of connections watching different submissions. So right after connecting, the client sends a subscribe message naming the submission it cares about, and the server records which connection wants which ID.

That two-step — connect, then subscribe — is where a real bug lived.

The fix is one extra step: the moment a client subscribes, the server also reads that submission's current status directly from Postgres and sends it immediately. If grading already finished, the client learns the verdict from the database instead of from a broadcast it missed. If grading hasn't finished, the snapshot simply says Queued and the live update arrives normally later.

This is the payoff of having a source of truth: the live layer is fast but forgetful, the database is durable but polled. Combining "send current state on connect, then stream changes" is the standard shape for real-time systems, and it's the same reason the queue carries only an ID.

07 — Being added next

Two extensions, and why they fit

The engine as a public API

Because execution and grading are already separated, the engine can be exposed directly: POST /api/v1/executions takes a language, source, and stdin, and returns output plus resource usage. The website keeps its own session-authenticated routes under /app/*; the public API authenticates machines with keys instead of humans with cookies.

That change is small in code and large in what it forces you to solve: hashed key storage, versioned routes, stable error codes, published documentation, and three separate protections that people often collapse into one — a rate limit (requests per minute), a quota (executions per day), and a concurrency cap (in-flight jobs per key). The third is the one that actually protects the system: a client submitting fifty slow jobs at a polite request rate can otherwise fill the queue and make everyone else wait.

Empirical complexity analysis

For an accepted submission, run it against generated inputs of increasing size, measure CPU time at each size, and fit the resulting curve against candidate models to report a measured growth rate. Wall-clock time is useless here — it includes scheduling noise and container startup — so the runner reads real CPU microseconds from the container's cgroup instead.

This is only possible because the execution layer is ours. It also introduces a second class of job, and that's the interesting infrastructure decision:

Reported honestly

The result is a measurement, not a proof. Over a 32× range of input sizes, O(n) and O(n log n) are usually indistinguishable from each other within timing noise — so the interface says "measured growth: O(n) or O(n log n)" rather than picking one. Knowing where the method stops being reliable is the part worth demonstrating.

08 — Interview answers

Say it out loud

The same content, compressed into the answers these questions actually want.

What did you build?

A sandboxed code execution engine, with an online judge built on top of it. Untrusted code runs in a throwaway container with hard memory and process limits and no network. Grading is asynchronous — the API writes the submission and pushes an ID onto a Redis stream, a worker pool picks it up, and results come back to the browser over WebSockets.

Why is the API fast if judging is slow?

Because the API never judges. A submission is one INSERT and one XADD, both sub-millisecond, and then the request is done. All the expensive work happens in a separate worker process, so API latency doesn't scale with how expensive grading is.

Why a queue rather than just calling the function?

Three reasons: it stops slow work from blocking the request thread, it survives a crash because an unacknowledged message stays in the consumer group's pending list and can be reclaimed, and it lets the API and the workers scale independently since they have completely different resource profiles.

How do you stop someone's code from taking down the machine?

Namespaces control what it can see, cgroups control what it can use. Memory is capped by the memory cgroup, so the kernel OOM-kills it rather than the host running out; process count is capped by the pids cgroup, which is the fork-bomb defence; the network namespace has no interfaces at all; and it runs as a non-root user. On top of that there's an application-level wall-clock timeout, because cgroups limit CPU time consumed, not real time elapsed — an infinite sleep burns no CPU but never finishes.

Tell me about a bug you found.

A race between finishing and subscribing. Pub/Sub only delivers to current listeners, and a trivial submission could be judged and announced before the client's WebSocket subscribe message even arrived — so the page waited forever for a broadcast that had already happened. I fixed it by sending a database-backed snapshot of the current status the moment a client subscribes, so the live channel is an optimisation rather than the only path.

What would you do differently at scale?

Reclaim stale pending messages automatically with XAUTOCLAIM instead of leaving that to a manual path; run the workers on dedicated hosts, since mounting the Docker socket effectively grants root on the host and that's the real reason this can't run on shared hosting; and add per-tenant concurrency caps so one client can't monopolise the worker pool.
